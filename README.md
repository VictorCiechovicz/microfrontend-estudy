# next16-microfrontends-lab

Projeto pessoal de estudo: um laboratório em monorepo para exercitar as funcionalidades do **Next.js 16.0 a 16.4.3** (Multi-Zones, Cache Components, Instant Navigations etc.) e **Module Federation** como contorno para compartilhar widgets entre zonas. Não é produto, não tem usuários reais e não guarda segredos: o único "segredo" é o valor de desenvolvimento `lab-dev-secret` do endpoint interno de invalidação (`LAB_INTERNAL_SECRET` o sobrescreve, ver "Variáveis de ambiente" abaixo).

Este README é um **mapa**: diz o que existe, onde está e em qual nota de `docs/features/` está o detalhe. O que cada funcionalidade de fato mostrou (inclusive o que não saiu como planejado) está nas notas.

Versões instaladas: Next 16.4.3, React 19.3.1, TypeScript 7.0.2, Rsbuild 2.2.14 + Module Federation 2.9.2, Node 26 (`engines`: >=24), pnpm 12.

## Como rodar

```bash
pnpm install
pnpm db:reset      # recria .data/lab.sqlite com os dados de exemplo (um banco vazio também é semeado na primeira abertura)
pnpm dev           # as quatro apps em modo desenvolvimento (turbo)
pnpm prod          # build + start das quatro apps (limpa o route-cache antes do start)
pnpm test          # testes unitários (Vitest) via turbo
pnpm e2e           # db:reset + build com a API de teste + Playwright (sobe as quatro apps em produção)
pnpm analyze       # next experimental-analyze no catalog (UI do analisador na porta 4000)
pnpm typecheck     # tsc --noEmit por app
pnpm lint          # Biome
```

Abra `http://localhost:3000`. Nunca acesse as zonas pelas portas 3001/3002 no dia a dia: o shell é a porta de entrada.

### Variáveis de ambiente

Para sobrescrever um valor, exporte a variável no shell: `LAB_LATENCY_MS=2000 pnpm dev`. O Turbo roda em modo estrito, então só repassa as variáveis declaradas em `turbo.json`: `LAB_INTERNAL_SECRET`, `LAB_LATENCY_MS`, `LAB_DB_PATH` e `SHELL_URL` (todas as tarefas), e `CATALOG_URL`, `ACCOUNT_URL` e `NEXT_PUBLIC_WIDGETS_URL` (no `build`, onde são embutidas; no `dev`/`start`, repassadas). O `.env.example` da raiz é só uma lista dos nomes e dos valores padrão: nem o Turbo nem o Next o leem. Um `.env` só valeria dentro de cada app (`apps/<app>/.env`), lido pelo Next daquela app, e as variáveis lidas pelo `@lab/db` ainda assim precisariam estar no ambiente.

| App       | Porta | Papel                              | Caminhos públicos (pelo shell)                      | Inspetor (`dev:inspect`/`start:inspect`) |
| --------- | ----- | ---------------------------------- | --------------------------------------------------- | ---------------------------------------- |
| `shell`   | 3000  | zona padrão, proxy de entrada      | `/` e o que não for de outra zona                   | 9229                                     |
| `catalog` | 3001  | catálogo, cache/prefetch/navegação | `/catalog/[lang]/...` (assets em `/catalog-static`) | 9230                                     |
| `account` | 3002  | conta, Server Actions, offline     | `/account/...` (`basePath`)                         | 9231                                     |
| `widgets` | 3003  | remote Module Federation (Rsbuild) | consumido no navegador                              | n/a                                      |

Usuários de exemplo: Ana (id 1), Bruno (id 2) e Carla (id 3), pelo login em `/account/login`.

## Arquitetura

```
                     navegador  http://localhost:3000
                          |
                 +--------v---------+
                 |  shell  :3000    |   proxy.ts: flag /catalog/sale, bloqueia /account/internal
                 |  (home estática) |   rewrites: /catalog/*  /account/*  /catalog-static/*
                 +---+----------+---+
        rewrite      |          |      rewrite
          +----------v--+    +--v-----------+
          | catalog     |    | account      |
          | :3001       |    | :3002        |
          | /catalog/.. |    | /account/..  |
          | proxy: 404  |    | proxy: login |
          +--+-------+--+    +--+-------+---+
             |       |          |       |
             |       +-- HTTP --+       |   POST /internal/revalidate  (segredo)
             |   broadcastInvalidation  |   shell <-> catalog <-> account
             |       (@lab/cache-sync)  |
             |                          |
   +---------v---------+      +---------v---------+
   | @lab/db           |      | @lab/db           |      um só arquivo SQLite
   | node:sqlite       +------+ (.data/lab.sqlite)|      compartilhado pelas zonas
   +-------------------+      +-------------------+

   navegador, depois da hidratação (nada disso roda no servidor):
   zona (catalog | account) --@lab/mf-host--> loadRemote --> widgets :3003 (mf-manifest.json)
        HelloWidget, CartWidget (header), Recommendations (produto)
        CartWidget <-> catálogo/conta: evento do navegador lab:cart-changed + /account/api/cart
```

Pacotes: `@lab/db` (SQLite e repositórios), `@lab/cache-sync` (vocabulário de tags e broadcast), `@lab/mf-host` (`RemoteWidget`), `@lab/ui` (componentes comuns), `@lab/tsconfig`.

## Resultados que surpreenderam / desvios

O plano previu uma coisa, o release instalado fez outra. Cada item aponta para a nota com as evidências.

- **`navigation()` não faz nada no catálogo.** Lá a página já é prefetchada de forma estática, então adiar as avaliações para a navegação não muda o que o Network mostra. É observável na página de pedidos da conta, que depende de dado por requisição. [navigation-prefetch](docs/features/navigation-prefetch.md#navigation-no-catálogo-sem-efeito-observável)
- **`prefetch()` aparece no bloco "Populares"**, o trecho independente da URL; é onde a diferença entre App Shell e prefetch por link se vê. [navigation-prefetch](docs/features/navigation-prefetch.md#prefetch-bloco-populares-na-página-de-produto)
- **Partial Prefetching fez ids de produto desconhecidos transmitirem um shell com status 200 antes do `notFound()`.** O `proxy.ts` do catálogo responde 404 antes. [isr-shell](docs/features/isr-shell.md#desvio-do-plano-404-de-verdade-para-produto-inexistente)
- **A tag `products:rankings` existe porque uma tag grossa num shell pré-renderizado anulou o stale-while-revalidate de `product:<id>`.** [cross-zone-cache](docs/features/cross-zone-cache.md#por-que-existe-productsrankings)
- **`setPriceAction` mistura dois mecanismos de propósito:** `updateTag(products)` (read-your-writes na lista) e `revalidateTag(product:<id>, 'max')` (SWR no detalhe). [cross-zone-cache](docs/features/cross-zone-cache.md#stale-while-revalidate-no-catálogo)
- **Zona fora do ar durante um broadcast:** se ela reinicia, volta fresca (o cache em memória morreu); se continua de pé mas rejeita o aviso, fica velha até o `cacheLife`. [cross-zone-cache](docs/features/cross-zone-cache.md#resultado-com-uma-zona-parada-execução-manual)
- **A estratégia `shared` do Module Federation só funcionou depois de compartilhar também `react-dom/client` e os runtimes JSX**, e o Next embute um React canary diferente do que o remote compila. [module-federation](docs/features/module-federation.md#o-que-falhou-na-primeira-tentativa-de-shared)
- **`instant()` exige `experimental.exposeTestingApiInProductionBuild`**, ligada só quando `EXPOSE_TESTING_API=1` (o script `pnpm e2e` faz isso). [instant-test](docs/features/instant-test.md#desvio-api-de-teste-no-build-de-produção)
- **`agentUpgrade: 'security'` é o padrão e não tem efeito visível; `turbopackPluginRuntimeStrategy: 'workerThreads'` cai de volta para processos filhos no Node 26.12.** [agents](docs/features/agents.md#o-que-agentupgrade-security-muda), [turbopack-flags](docs/features/turbopack-flags.md#fallback-de-worker-threads-no-node-26-linha-real)
- **O Next 16.4 persiste renders de runtime em `.next/server/route-cache`.** Entre execuções isso faz o cache sobreviver ao reinício; por isso `pnpm prod` e `pnpm e2e` apagam a pasta antes do `start`. [cross-zone-cache](docs/features/cross-zone-cache.md#resultado-com-uma-zona-parada-execução-manual)

## Module Federation é um contorno

O Turbopack, bundler do App Router, não tem plugin de Module Federation, e o `nextjs-mf` só serve ao Pages Router com webpack. Então **as zonas Next não participam da federação no build**. O que o lab faz é um contorno:

- `apps/widgets` é um app **Rsbuild** que expõe `HelloWidget`, `CartWidget` e `Recommendations` e publica `mf-manifest.json` na porta 3003.
- As zonas carregam os widgets **só no navegador, depois da hidratação**, com o runtime do MF (`@lab/mf-host`: `loadRemote` num `useEffect`, error boundary, fallback). No servidor o widget não existe e o HTML sai sem ele.
- Estratégia que venceu o spike: `shared` (host e remote dividem uma única instância de `react`, `react-dom`, `react-dom/client` e JSX runtimes). A alternativa `mount` (cada widget com o seu React e um root próprio) também funcionou e é a rota de saída se um canary do React do Next deixar de ser compatível.
- Diferenças em relação a Multi-Zones e o resto: [module-federation](docs/features/module-federation.md#diferença-para-multi-zones).

## Limitações conhecidas

- **Aviso de invalidação perdido:** se uma zona está fora do ar (ou rejeita o segredo) durante um broadcast, ela não é reavisada; o `cacheLife` é a rede de segurança. [detalhes](docs/features/cross-zone-cache.md#zona-fora-do-ar)
- **`useOffline` só vale em produção** e em navegação suave/Server Actions da página atual: recarregar sem rede continua falhando, e em `next dev` o teste não é confiável. [offline](docs/features/offline.md#versão)
- **Widgets Module Federation não renderizam no servidor** (sem SSR, sem HTML do widget para crawlers) e dependem de o `:3003` estar no ar; sem ele aparece o fallback.
- **Cache de dados em memória por processo:** cada zona tem o seu; a coerência entre zonas é por broadcast HTTP, não por infraestrutura compartilhada.
- **Endpoint `/internal/revalidate` do shell fica alcançável de fora**, protegido só pelo segredo de desenvolvimento; é escolha consciente de laboratório. [cross-zone-cache](docs/features/cross-zone-cache.md#exposição-pelo-shell)
- **`workerThreads` é ignorado no Node 26.12** (o Turbopack o desliga por causa de um bug de teardown de workers com addons nativos).
- Não é um modelo de produção: sem autenticação real (login por cookie de id), sem migrações, SQLite local compartilhado por três processos.
